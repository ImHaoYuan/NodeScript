### 2026-10-06 —— 批 61：输入通道三选一（`auto`/`adb`/`root` 平级、必须显式、绝不降级）+ 引入 Shizuku

- **驱动**：用户口径「点击什么的不要按降级使用，脚本内传入 auto 表示启用无障碍，adb 则是 adb，
  root 则是 root」，三问三答锁定作用面（「两者都管（含节点 click）」）、选择方式（「两者都要」
  = 按调用 + 会话级）、缺省（**「必须显式传，无默认」**），随后一句「引入」= 真接 Shizuku 而不是留桩。
  口径全文见 [`design-decisions.md`](../design-decisions.md) 第 35 项。
- **改的是什么**：§9.3 的输入面从「一条 `InputProvider` 实现」改成**三条平级通道 + 显式选路**。
  `InputChannel{AUTO,ADB,ROOT}`（`:domain`，`ofWire` 大小写不敏感、未知取值抛）；`ShellInputProvider`
  （`:platform:system`，`input tap`/`input swipe`，`ShellMode.ADB|ROOT`）；`ShizukuInput`
  （`:platform:capabilities`，唯一 `android.*`/`rikka.shizuku.*` 接触点）。
- **「不降级」是判据不是口号**：指定的那条不可用 → `ERR_PERMISSION_DENIED`（带引导），**绝不换通道**。
  与 §9.5 的 `DEGRADED` 哲学刻意相反 —— 三者**可观测后果不同**（无障碍注入会被前台应用看出、
  root 在系统层不留无障碍痕迹、adb 的进程身份是 shell），对签到/抢购/压测这类场景
  **走了哪条通道是语义的一部分**。
- **「必须显式」落成两处**：载荷 `channel` 或会话级 `a11y.setInputChannel`，**都没有 → `ERR_INVALID_PARAM`**。
  实现上**刻意不预置 `auto` 缺省** —— 预置等于「什么都没说 = 走了无障碍」，那正是本机制要消灭的静默。
  **本批中途纠过一次自己的错**：初版把会话默认值写成 `AUTO`，与用户「无默认」的答复相反，已改回 `null`
  并连带改契约/JS/全部调用点/测试（`NewlineFrameServerTest` 的跨连接断言因此从 `AUTO` 变 `NO_SESSION`）。
- **会话态挂「连接」不挂「handler」**：handler 是全局单例（一套 handler 服务所有脚本），字段级会话态
  会让脚本 A 设的通道**静默漏给脚本 B**。改为 `InputChannelSession`（`AbstractCoroutineContextElement`），
  `NewlineFrameServer` 每连接建一个 → 隔离是**结构上**的，不靠人记得清。
- **节点动作在非 auto 通道降级为坐标注入**：`click`/`longClick`/`scroll` 在 `auto` 走节点语义
  （`ACTION_CLICK`/`ACTION_LONG_CLICK`/`ACTION_SCROLL`），`adb`/`root` 没有节点语义（shell 只有 `input`），
  改解 `bounds` 再注入（点中心 / 按方向在节点内划一条，手指方向与内容方向相反）。语义是
  「点这个控件**所在的位置**」。**`copy`/`paste` 例外**：纯语义动作、没有第二条通道可选，**不要求** `channel`
  —— 这一刀是被测试逼出来的（复用 `nodeAction` 会让它们开始要一个没有意义的参数，`A11yNamespaceHandlerTest` 当场红），
  故拆出 `refAction`。
- **shell 面只有直线（如实写在契约里）**：`input tap`/`input swipe` 没有轨迹，`gesture` 逐笔画串行注入、
  每条只取首尾两点；真轨迹要 `sendevent`（**未落地**）。`canPerformGestures` 在 `auto` 问服务能力位，
  `adb`/`root` 恒 `true`（没有对应开关）；真失败以**命令退出码**出现在动作调用里，**不折成 false**
  （false 的语义是「系统拒绝这次注入」，与「这条通道没了」是两回事）。
- **引入 Shizuku 依赖**：`dev.rikka.shizuku:api` + `:provider` 13.1.5 落
  `gradle/libs.versions.toml`（**冻结文件**，第 35 项即维护者授权）与 `platform/capabilities/build.gradle.kts`。
  代码走**反射**（JVM 单测跑 mock android.jar，碰 `Shizuku` 静态初始化即炸），失败面全部折成
  `ERR_PERMISSION_DENIED`（「没装」与「版本不兼容」对用户是同一句话）。**`<provider>` 节点必须显式声明**
  —— 解包 `provider-13.1.5.aar` 实测 AAR 只带 meta-data 与类、不带节点；authority = `${applicationId}.shizuku`，
  `exported=true` + `moe.shizuku.manager.permission.API_V23` 是它的**设计形态**。合并后 manifest 实测
  authority = `com.autoscript.shizuku`。**依赖停更于 2023-09**（`lastUpdated=20230921`）。
- **接线是探测式的**：`PlatformWiring` 只在 `ShizukuInput.isAvailable()`（装了**且**服务活着，两问都要）时
  登记 `adb` 通道；`root`/`auto` 恒登记。**登记与否只决定「这条通道现在有没有」，绝不改变调用方选的那条**。
- **JS 侧不预检**（与 `engines.exec` 的 `timeoutMillis` 同一条「校验不写两遍」纪律）：
  `ChannelOptions.channel` 类型上仍可选（设过会话值后省略是**合法**写法，类型系统看不见会话状态），
  判据只有宿主 handler 一处。
- **契约**：§9.3 改标题为「输入通道（auto / adb / root）」+ 必须显式/例外/接线三段；§12.3 表 a11y 行补
  `setInputChannel`；§12.3.1 示例重写并**在 `dist` 上逐字跑过**（facade 文档纪律）；`docs/api` 与
  `wire-types.ts` 走生成器重跑，零手工编辑。
- **门**：13 个测试任务 **1342 例 0 skipped 0 failed**（新增 `A11yInputChannelTest` 与
  `ShellInputProviderTest` 两个套件）、detekt 过、`npm test` 196 例（195 过 + 1 例既有环境跳过）、
  `npm run lint` 过、`gen:wire`/`docs:api` 零漂移、文档链接门 444 条全绿。
- **未真机验证（诚实缺口）**：设备道 2026-10-06 已裁（第 34 项 / backlog B3/E3）。JVM 侧钉住的是
  「命令怎么拼、退出码怎么判、通道怎么映射、缺席怎么拒」；**真机上装好 Shizuku 后能不能注进去、
  `bounds`→坐标这条映射准不准、`sendevent` 真轨迹要不要做，尚无人跑过** —— 缺口登记进 backlog B14。

### 2026-10-06 —— 批 60：B13 `auto.zip.extract` 体积上限（与 B12 同一个洞，这个面更常被摸到）

- **缺口**：`JdkZipArchiver.extract` 的落盘是 `Files.copy(ins, out, REPLACE_EXISTING)` **直接写终态路径**，
  **零上限、零可用空间守卫**。`auto.zip.extract(archive, targetDir)` 是**生产接线且脚本可达**的
  （`PlatformWiring.kt` → `AppShell.kt` 注册 `zip` 命名空间；JS 侧 `zip.ts`），而契约 §9.6 这一面
  只写了 zip-slip 一条底线 —— **一个 1 MB 的 zip 可以写出 10 GB**，脚本作者不会想到要防它。
  比 B12 更直：B12 是「用户从 SAF 选错文件」，这条是**脚本自己给的路径**。
- **两道闸**（都要，缺一不可）：单条目 `MAX_ENTRY_BYTES = 256 MiB` 防「一个巨物」，
  整包合计 `MAX_TOTAL_BYTES = 1 GiB` 防「一万个小东西」—— 后者是单条目闸挡不住的那类。
- **判据分两拍，与既有的 zip-slip 同一结构**：第一拍按包的**声明**早退（诚实炸弹在写任何
  字节之前就被拦下，与 zip-slip 的「先验后写」同语义），第二拍在字节流经过的地方按**真读出来的
  字节数**再判一次。**B12 学到的那条在这里复用了**：`ZipEntry.getSize()` 是包自己声明的数、
  可以撒谎，所以真正的上限只能在 `copyCapped` 里 —— 那是唯一一处字节还没写出去的地方。
- **错误码 `ERR_INVALID_PARAM`（与 zip-slip 同码）**，不是 `ERR_DISK_FULL`：超限是**输入**的问题
  （这个归档本身不合格），不是目标盘的问题。两者混用会让「盘满了」与「包是炸弹」报同一个错，
  用户没法判断该删东西还是换文件。**不查剩余空间** —— 那是配额面的事（§10.9 UX 5）。
- **半截文件要删**：第二拍拦下时把已写的那一条 `deleteIfExists`（它已确定是废的，留着只会让
  用户以为「解出来一部分」）。先前已完成的条目留在盘上 —— 那与任何中途 IO 失败同形，本类不改
  这个既有语义；**诚实炸弹在第一拍就零写入，走不到这里**。
- **测试缝**：两个上限走构造参数（`JdkZipArchiver(maxEntryBytes = …, maxTotalBytes = …)`，生产走
  `SystemSpis.of` 的无参构造）。理由同 B12：边界要按真值测就得造 256 MiB+ 的条目，而**为一条不该
  落盘的条目先写满 256 MiB 磁盘**是拿边界的坑去测边界。新增 4 例：诚实炸弹先验后写零字节、
  撒谎声明被计数闸兜住、总量超顶（8×8KiB，单条都不超顶）、恰好到顶放行（上限含等号）。
- **契约**：§9.6 加体积上限一段（两道闸、两拍判据、为什么不用 `ERR_DISK_FULL`、为什么不查剩余空间）；
  §12.3 接线表 zip 行的钉子补「体积上限」；`zip.ts` 的 KDoc 补一句（typedoc 的**文档入口面**只展开
  `auto` 与 `AutoNamespace` 的声明，`auto.zip` 属性引用不在内，故 `docs/api` 零 diff —— 这是实测的
  边界，不是漏跑）。
- **门**：`:platform:system:test` **196 例 0 skipped**（+4）、`:platform:system:detekt` 过、
  `bridge/js` 的 `npm test` 193 过 1 例既有环境跳过 + `npm run lint` 过、`gen:wire` / `docs:api` 零 diff、
  文档链接门绿。

### 2026-10-06 —— 批 58：B12 离线 bundle 体积上限（两道闸 + 可注入的测试缝）

- **缺口**：`NpmOfflineBundleImporter` 收的是**用户从 SAF 递进来的外部文件**，整包与单条目都没有上限
  —— `zf.getInputStream(e).readBytes()` 对单条目是无界的，一个 4 GB 的条目就是一次 OOM，而这条路径的
  调用方**可能只是选错了文件**（视频、系统镜像、整个 Downloads 打成的一个包）。
- **两道闸**：整包 `MAX_BUNDLE_BYTES = 512 MiB`（解包前先看，判据是 `Files.size` 而**不是** zip 声明的数）
  + 单条目 `MAX_ENTRY_BYTES = 64 MiB`。超限**整包拒收**，不截断 —— 截断一个 zip 得到的不是「半个包」
  而是一批摘要对不上的条目，只会把「选错文件」变成「一屏看不懂的 rejected」。
- **单条目那道闸的形态改过一次（本批最值得记的）**：第一版是「先看 `ZipEntry.getSize()` 声明大小，
  读完再用 `data.size` 兜底」。**先证伪再定稿**：写了个探针把中央目录与本地头里的未压缩大小都改成
  100（载荷 5000 字节），`ZipFile` 报 `declared=100` 而**真读出来仍是 5000** —— 声明是包自己写的，
  改得动，所以「先看声明」只能省事、**不能当保证**，而兜底那一步内存已经吃进去了。定稿改成
  `readCapped`：**读到顶就停**，缓冲上界 = cap + 一个读块，与条目真实大小无关。声明超顶的那道便宜的
  早退保留（省一次读），但它不是上限。
- **可注入的测试缝**：`import(zipFile, cacheDir, maxBundleBytes, maxEntryBytes)`（`internal`，默认值即那两个
  常量，生产入口 `import(zip, cacheDir)` 一行转发，两个入口同一段循环）。理由写在 KDoc 里：边界要按真值
  测就得造 64 MiB+ 的条目，而**为一条不该进内存的条目先吃满 64 MiB 内存**是拿边界的坑去测边界。
- **错误码口径**：`InstallCoordinator.importOfflineBundle` 把超限的 `IllegalArgumentException` 翻成
  `ERR_INVALID_PARAM`（其余仍 `ERR_FILE_NOT_FOUND`），原文（实际字节数 + 上限）保留给用户。两者对用户的
  下一步动作完全不同：**去重选文件** vs **去查 SAF 副本有没有落地**。超限同样入史（不留痕等于没发生）。
- **契约**：§10.9 UX 4 加一段上限口径（两条闸、整包拒收、`ERR_INVALID_PARAM`、为什么）。
- **门**：`:app-service:npm:test` **197 例 0 skipped**（本模块 192 → 197；`NpmOfflineBundleImporterTest`
  9 → 13 例，`InstallCoordinatorTest` 加 1 例）。其中超限那条**真写 513 MiB**（cacache 内容寻址要求条目名 =
  内容摘要，所以只能靠「很多条小条目」把整包撑过顶 —— 那正是这条路径的真实形态）；撒谎条目那条**真造了
  一个改过声明的 zip**。文档链接门 436 条绿。
- **未做（如实登记）**：**不按剩余磁盘空间判**（那是配额面的事，判据在安装会话，不在导入器）；**不做流式
  解包**（上限挡住之后没有这个必要 —— 真需要是另一个问题，见本文件批 51 的口径）。
