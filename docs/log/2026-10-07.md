### 2026-10-07 —— 批 65：PR #44 外审（`main` 侧）—— release 包 R8 把 Shizuku 反射面删光 + `newProcess` 取法错（包内可见声明类）+ 台账被覆盖

- **驱动**：用户「review 审查 pr，代码有问题请修改」。被审对象 = fork `ImHaoYuan/NodeScript` 的
  PR #44（`Updated UI`，HEAD `822d307`，本地分支 `review/pr44`）。**结论：两处是真错、且都在
  `main` 侧的既有文件上** —— PR 自己没有引入坏代码，它只是把两处**潜伏的坏**接通了电。
- **① release 形态 R8 把 Shizuku 反射面删光**（PR 给 `:app` 加了 `release { isMinifyEnabled = true }`，
  这是本仓第一次真跑 R8）。原 `app/proguard-rules.pro` 的判据是「按字符串找类只有一处」，
  **该判据本身是错的**：`Class.forName` 在 main 源集里 3 处（`:app` 1 + `ShizukuInput` 2），
  `getMethod` 9 处（`ShizukuInput` 8 + `ProcessLauncher` 1）。实测证据（改前那次构建）：
  `mapping.txt` 里 `rikka.shizuku.Shizuku -> O2.c`、`getBinder() -> call`；`usage.txt` 把
  `getBinder()` / `pingBinder()` / `IShizukuService$Stub.asInterface` / `ShizukuRemoteProcess`
  四个方法**全部列为已删**。症状不是崩溃而是**静默**：release 包上 adb 通道恒不可用，
  `PlatformWiring` 不登记 `InputChannel.ADB`，用户看到的是「Shizuku 未安装」。
  **改法**：`proguard-rules.pro` 逐条补 `-keep`（**不是** `-keepnames` —— 后者带 `allowshrinking`，
  只保名不保代码，对"只被反射调到"的成员等于没写），并订正那份过期判据。
  **改后实测**（`:app:assembleRelease` 重跑）：`mapping.txt` 四个类**零重命名**；
  `usage.txt` 里四个方法**一条都不在删除清单**（`Shizuku` 那条仍删 `newProcess`/`requestPermission`
  等**本应用不调**的成员 —— 说明规则是精确生效的，不是"整类全保"）。
  APK 1,587,512 → 1,590,308 字节（+2.8KB，就是那四条规则）。
- **② `newProcess` 从错误的类上取**（**PR 之前就错**，`main` 与 merge-base `39806ff` 上逐字相同）。
  原代码 `service.javaClass.getMethod("newProcess", …)`：`asInterface` 返回的是 AIDL 生成的
  `IShizukuService$Stub$Proxy`，那个类**包内可见**（`javap` 无 `public`），在它上面取到的
  `Method` 带着"声明类不可见"的访问检查，`invoke` 抛 `IllegalAccessException` —— 而 `step`
  把 `ReflectiveOperationException` 折成同一句拒绝，于是**adb 通道永远不可用且提示指向假原因**。
  同一处的第二个错：`invoke(service, argv, null, null)` 给 `String[]` 形参传 `null`（AIDL 生成的
  proxy 按 `@NonNull` 解引用）。**改法**：方法从**公开接口** `moe.shizuku.server.IShizukuService`
  上取（声明类可见 → 正常分派到实现类），env 传 `arrayOf<String>()`。两条都在独立 JVM 实验里
  复现过（包内可见声明类的 `Method.invoke` 抛 `IllegalAccessException`；换公开接口后 `invoke` 正常）。
  **仍未真机验证**（backlog B14 原样有效）：本机只能钉"取法与签名正确"，注得进去与否要真机。

### 2026-10-07 —— 批 64：引导文案改成「与三态无关」（A8 结项）+ `ADB_INPUT` 三态随批 61 修正 + 大文件余量收口（D7 结项）

- **A8（引导文案与三态读数自相矛盾）** —— 裁定**选项①**：八条文案逐条重写成「这项能力是干什么的 +
  怎么让它可用」，**显示逻辑不动**。理由是 `CapabilityRow.guide` 的 KDoc 描述的是**意图**
  （文案自带当前态那句、呈现层不按三态猜），而 `guideText` 八条里**六条按拒绝态起句** ——
  意图与数据对不上，改数据这一头。**不**推翻「永远显示」口径：撤下显示是批 47 已经做过的事
  （用户口径「去除各个权限的描述」，设置页不再渲染 `guide`），本项管的是**将来再渲染时**文案必须自洽。
  钉子：`PermissionCenterTest` 新增两条 —— 「不按拒绝态起句」（`startsWith("未"/"没"/"不")` 即红）
  与「`ADB_INPUT` 文案不承诺降级」。口径全文见 [`design-decisions.md`](../design-decisions.md) 第 38 项。
- **顺带修正一处过期口径（本批真正的行为变更）**：`AndroidSystemStateReader` 里 `ADB_INPUT`
  此前是**恒 `DEGRADED` 常量**，理由写的是「Shizuku 尚未集成，但引导文案承诺的降级路径真实存在」。
  **批 61（§9.3 三通道三选一）已经把那条路废掉了** —— 指定 `adb` 而不可用就是 `ERR_PERMISSION_DENIED`，
  绝不改用别的通道；那条「降级路径」不存在了，继续报 `DEGRADED` 是拿旧口径骗人，文案里那句
  更是对用户的假承诺。改法：探针加 `adbInputAvailable()`（转问 `ShizukuInput.isAvailable()`，
  **唯一**的 Shizuku 接触点仍在平台模块），映射改成 `就绪 → GRANTED / 不就绪 → DENIED`
  （与无障碍 / root / 使用情况访问同档：都没有替代路径）。**出厂态 DENIED 集合随之从四种变五种**，
  `AndroidSystemStateReaderTest` 那条钉死的断言同批更新并写明为什么。
  边界如实登记：Shizuku 在跑但**尚未授权本应用**时也判 `DENIED`（binder 问询拿不到服务），
  文案因此把「授权本应用」与「装/启动 Shizuku」并列写；真机上「装好之后能不能注进去」仍未验（backlog B14）。
- **D7（大文件余量）结项** —— 先纠度量口径：两个文件都**注释密集**（KDoc 近半行数），裸行数高估了问题。
  `Scheduler` 的类体是一台**单一内聚状态机**，两个大方法要外迁得把八九个构造参数摊成 `internal`
  ——**拿封装换行数，不划算**；真接缝是三个不属于这台状态机的顶层声明（`ScheduledTask` /
  `RecoveryRecord` / `DefaultDeadlines`），各自成文件，语义逐字未改。`AppShellApplication` 的
  **读侧**（`HostSummary` 各实现）只是转手 `AssembledShell` 的字段、**零重复不变式**，不搬；
  **写侧**取一个刀口 —— `installWithFiles` 里四类 APK 资产的读法各带一条降级口径，四段 `try/catch`
  混在九十行的具名参数表里读不出「为什么这条这么吞」，抽成 `shell/AssetsRead.kt`（**该文件不可单测**：
  参数是 `AssetManager`，JVM 造不出真实例 —— 已写进它的 KDoc，免得将来以为 `shell/` 下的都自带单测缝）。
  **行数不写进文档**（会漂）。口径全文见 [`design-decisions.md`](../design-decisions.md) 第 39 项。
